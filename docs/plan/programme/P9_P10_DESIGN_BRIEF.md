# Design brief: a build per path (P9) and reader levels (P10), 2026-11-11

Two designs, written before wave C touches the pipeline (L9) and the site (L10), so those lanes
change each file once. A design is a document; this brief asks for no code.

## P9: a build per path, a site that switches paths

Owner: "easily and dynamically switch paths and choices on the website"; "each path makes its own
version of json, params, formulas, sections so the paper, params and formulas update with the
chosen path"; "run simulations and tests on all branching paths as bugs are fixed to find whether
old paths are working or better". A rejected option stays off, keeps its no-go label, and is
still run and validated.

What exists (read these first, narrowly):
- `src/metaphysica/simulations/core/variants/`: 26 forks; `resolve`, `departures`, `compatible`,
  `load_selection`, `active_selection`, `report`; override by `METAPHYSICA_VARIANT_<FORK_ID>`.
- `src/metaphysica/build.py`: the `STEPS` table (about 100 steps), `--out`, `--fast`, `--only`,
  `--keep-going`, `write_path_graph`, `begin_fork_reads` and `merge_fork_reads`.
- `src/metaphysica/testground/`: `sweep`, `runner`, `switches`, `configurations`, `rank.py`,
  `results`; `generators/generate_path_ranking.py` publishes a ranking; the last ranking is
  stale (`docs/plan/programme/stale/path_ranking_137dd42.json`).
- `src/metaphysica/generators/`: what writes `parameters.json`, formulas, sections, the paper.
- `src/metaphysica/website/`: the site templates and scripts the build copies out.
- Output directory: `METAPHYSICA_OUT` or `--out`; default is the sibling site repository.

Facts to design against (measure, do not assume): a fast build is about 400 s for one path;
the site is static (GitHub Pages, no server); values that cannot be derived on a path are
NOT_EVALUABLE there and are never borrowed from the default path.

The design must answer:
1. Path identity: an id for a selection over all forks that is stable, short, readable, and
   survives a new fork being added. Which paths are built: every single-fork departure from the
   default, named combinations, the owner's candidates; who decides.
2. Layout: where a path's artifact set lives (`AutoGenerated/paths/<path_id>/...` is a starting
   point, not a ruling), what is in it, what is shared, the index file and its schema. The
   default path stays where it is today. Size budget for N paths, measured from a real build.
3. Build: which steps depend on the path and which do not (use the fork-read tracking), how a
   sweep avoids rebuilding the rest, where failures of one path are recorded without stopping
   the others, the wall-clock cost for 30 and for 100 paths, what CI runs and what runs offline.
4. Evaluation: one record per path with for, against, alignment and evidence: ladder checks,
   scored rows, chi2 over the same row set, NOT_EVALUABLE counts, the no-go label and its
   reason. How ranking handles paths that score fewer rows. How a re-run after a fix wave
   reports a change of rank as a finding.
5. Site: the switcher (where it sits, how the choice is kept in the URL, how pages load the
   chosen set, what a page shows for NOT_EVALUABLE, how a no-go path is marked on every page),
   the paper per path (sections JSON per path; which paths get a PDF).
6. Tests: one per rule above that can be broken (a borrowed value, a stale index, a path whose
   label says no-go but whose page does not).
7. Order of work as lane-sized steps with owned files, each with an acceptance test.

## P10: reader levels

Owner: turn the beginner primer into the beginner section of the site, in three levels:
1 general public (high-school physics); 2 enthusiast (about two years of undergraduate
physics); 3 physics graduate. The main site and paper stay at research level (level 4).

Source: `docs/plan/programme/reader_levels/primer_v1.html` (diagrams, analogies, written for
level 1 to 2). The model is speculative and unvalidated and every level says so plainly.

The design must answer:
1. Content map: the topics of the section, and for each topic what each level says (same
   skeleton, three depths), with the level 4 page it leads to.
2. Source format in the engine: templates plus data, so every number comes from the registry of
   the chosen path and no page is edited by hand in the site repository. Where diagrams live
   (inline SVG that reads in light and dark themes).
3. Generation: the build step, its outputs, how it follows the P9 path choice, what it shows
   when a quantity is NOT_EVALUABLE or a claim is falsified on the chosen path.
4. Navigation: how a reader picks and changes level, how the level is kept, entry from the home
   page, links up and down between levels.
5. Checks: no literal framework number in a template; every claim carries its status label
   (derived, fitted, ansatz, falsified); reading-level checks that can run in a test.
6. Order of work as lane-sized steps with owned files, each with an acceptance test.

## Rules for a designer
- Read-only on code. Write only the file your prompt names, under `docs/plan/programme/design/`.
- Read narrowly: signatures and tables, not whole files. Cite file:line for every "exists".
- Say what you measured and what you assumed. A cost with no measurement is an assumption.
- 300 lines at most per proposal. No code beyond a schema or a ten-line sketch.
