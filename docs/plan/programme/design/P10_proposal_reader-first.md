# P10 proposal: reader levels, angle "reader-first" (2026-11-11)

Answers the "P10: reader levels" section of `docs/plan/programme/P9_P10_DESIGN_BRIEF.md:51-72`.
Method: list what a reader does, write down what each step promises the reader, and derive the
URLs, navigation and page structure from those promises. Paths in `PrincipiaMetaphysica/...` are
in the sibling site repository (the default build output, brief line 24).

## 0. What the reader does, and what we promise

| # | Reader journey | Promise (invariant) |
|---|---|---|
| J1 | Arrives on the home page and does not know the field | One obvious "start here" right after the research notice; picks a level by their background, not by a label |
| J2 | Arrives from a shared link or a search result deep inside a level page | The page says what it is (level, path, speculative status) before any claim, with no JS |
| J3 | Finds the text too easy or too hard halfway down | One click moves to the same topic, the same claim, at another level |
| J4 | Wants the real thing | Every topic links to its research (level 4) page, and the research page links back down |
| J5 | Has chosen a non-default path, possibly a no-go one | Every level page names the path and its label; no number from another path is shown |
| J6 | Reads with no JS, prints, or uses a screen reader | Text, numbers, statuses and level links are in the HTML; JS only adds comfort |
| J7 | Reads only level 1 | Is told every caveat that the level 3 reader is told (shorter, never fewer) |

These give seven rules, used below as R1..R7 with the same numbers.

## 2. Source format in the engine (Q2)

From this angle, three needs only; the file format itself is left to the other proposals.
- One source file per topic holding all three levels claim by claim, side by side, so an author
  who softens level 1 sees the level 3 caveat next to it. A level is never its own file.
- A claim's prose never states its own status; the status sentence comes from a fixed phrase
  table keyed by the reader label (section 5), so a path that changes the status cannot leave the
  prose saying the old one.
- Diagrams: inline SVG inside the topic file, coloured only through CSS tokens with light and
  dark values as in the primer (`primer_v1.html:8-20`). The site is dark-only today (only
  `css/pm-paper-tooltips.css` has `prefers-color-scheme`), so the level pages carry their own
  token sheet. One SVG serves levels 1 and 2 where the picture is the same; level 3 may add labels.
  Every SVG keeps `role="img"` and an `aria-label` as the primer does (`:170`, `:194`).

## 3. Generation (Q3)

- Step: "Build reader levels", after "Build the geometry-to-physics walkthrough"
  (`build.py:390`), because it reads the same parameters, formulas and validation report.
- Outputs for the default path: `Pages/learn/index.html`, `Pages/learn/level-1.html`,
  `level-2.html`, `level-3.html`, and `AutoGenerated/learn/claims.json` (claim id to value,
  unit, reader label, registry status, NOT_EVALUABLE reason).
- Every number and status is in the HTML at build time (R6). Spans also carry the claim id so
  the path loader can replace them.
- Other paths: the step writes one `claims.json` per path wherever P9 puts a path's artifact set.
  The level page loads it for `?path=` and swaps values, chips and status sentences. One HTML file
  per level for all paths keeps one URL per level (section 4). Rendering three HTML pages per path
  is the fallback if P9 builds pages per path anyway.
- NOT_EVALUABLE on the chosen path: the value slot reads "This path cannot compute this number"
  with the reason on hover and in the level 3 text; never main's value (R5). If the path's
  `claims.json` is missing, every value slot shows that phrase and the status strip says "results
  for this path were not built". The page never falls back to main (contrast
  `pm-path-context.js:16`).
- Falsified on the chosen path: the claim stays in place (it is never removed), with the red
  "Ruled out" chip, and the topic's opening line counts the ruled-out claims in it. Nothing says
  what another path would give, except one link to `Pages/paths.html#<path>`.
- No-go path: the status strip shows "This path was rejected: <reason>" on every level page,
  taken from the path index label (`paths/index.json`) and P9's no-go reason.

## 4. Navigation (Q4)

URLs (the level is part of the file, so a shared link always opens the level it names):

```
Pages/learn/index.html                     chooser: status strip, three level cards, topic list
Pages/learn/level-{1,2,3}.html             one page per level, anchors = topic ids from section 1
Pages/learn/level-2.html#holes             a topic;  #holes.euler  a claim (same at all levels)
...?path=<id>#holes                        a path, kept by the existing link keeper (:224-229)
Pages/beginners-guide.html                 generated stub: link plus meta refresh to learn/
```

No `?level=` parameter: a query state could disagree with the file, and with no JS it would do
nothing.

Picking a level (J1). `learn/index.html` shows three cards, each titled by the reader's
background ("I did physics at school" / "I studied some physics at university" / "I have a
physics degree"), with the same claim (`holes.euler`) quoted at that level. The reader picks by
reading a sample. A line under the cards: "Not sure? Start at level 1: every section has a
harder link." No quiz (assumed: a quiz adds a step and is not needed when moving level is one
click).

Changing level mid-page (J3).
- A sticky level bar under the path bar: `Level: 1 School | 2 Undergraduate | 3 Graduate |
  Research ->`. Each entry is a plain link to the same topic on the other level page, with the
  current level marked `aria-current="page"`. A 20-line script updates the hashes to the topic
  or claim in view; without JS the links point to the top of the page.
- At the end of every topic, rendered in HTML: "This topic at level 1 · 2 · 3 · the research
  page". This works with no JS and in print.
- The target page scrolls to the same claim. If the claim has no text at that level (forbidden
  by R7, so a build failure), the topic anchor is the target.

Keeping the level. The URL is the state: file, `?path=`, `#anchor`. localStorage `pm.level`
keeps the last level and topic only to show "Continue at level 2, Counting holes" on the home
page and on `learn/index.html`. It never redirects, and every read and write is in try/catch.
The path keeps its existing store (`pm-path-context.js:4`).

From the home page. A "Start here" card directly after the research notice
(`index.html:553-566`), which stays first, replaces the pill at `index.html:977`. Header link
`pm-header.js:36` becomes "Learn" pointing at `learn/index.html`. The 13 inbound links keep
working through the stub.

Up and down (J4).
- Up: each topic's research link comes from the content map. Level 1 and 2 readers see one line
  first: "The research pages use the registry's own status words; the glossary maps them."
- Down: research pages that appear in the content map get a "New to this? Read it at level
  1 · 2 · 3" line. It is generated from the same map in reverse and inserted by the template
  of each level 4 page (owned by L10), not typed in.

Status on every page (J2, R2). A strip before the first heading, in HTML, never inside
`<details>`, printed too:
"Speculative and unvalidated. Not peer reviewed. Fit to measurements today: {verdict phrase}.
Path: {label}{, rejected: reason}. Built {date} from {commit}." At level 2 and 3 it adds
"chi2 {value} over {rows} rows". Every field is generated; the verdict comes from the registry
verdict (POOR_FIT today), never from `statistics.json`'s `status` string.

## 5. Checks (Q5)

Reader labels (R7). The registry carries 20 status values on parameters (measured, see
"Measured"). Each maps to one reader label; a status with no mapping fails the build (fail early).

| Reader label (level 1 words) | Registry statuses | Chip |
|---|---|---|
| Derived ("worked out from the shape") | DERIVED, GEOMETRIC, COMPUTED, PREDICTED, PREDICTIONS | neutral |
| Fitted ("tuned to match a measurement") | FITTED, CALIBRATED, FITTED_COMPOSITE, RETRODICTED_VARIANT | amber (as `:25`) |
| Ansatz ("assumed, not derived") | ANSATZ, SPECULATIVE, TOPOLOGY_CANDIDATE | amber |
| Falsified ("ruled out by measurement") | FALSIFIED, FAILING | red (as `:26`) |
| Measured ("known physics, not the model's claim") | MEASURED, ESTABLISHED | grey |
| Not evaluable ("this path cannot compute it") | NOT_EVALUABLE | grey, hatched |
| (no mapping yet: build fails if a claim uses one) | SYSTEM, VALIDATION, FOUNDATIONAL, TERMINAL, TENSION | n/a |

Level 2 shows the registry word in brackets after the reader word; level 3 shows the registry
word with a link to its definition.

Tests, one per rule that can be broken:
1. No literal framework number: outside value slots, a template's text has no digits except in
   elements marked as an example (analogies, the sigma calculator defaults) and SVG geometry.
   "26" is a framework number and comes from the registry. The primer has 251 numeric tokens
   (measured), so the migration classifies each.
2. Every claim element has a chip, and the chip and the status sentence agree with the registry
   for the built path.
3. Caveat parity (R7): for each claim id, the reader label is the same at levels 1, 2 and 3, and
   every claim id exists at all three levels.
4. Status strip: present on every learn page, before the first `<h2>`, not inside `<details>`,
   with the verdict and the path label filled.
5. Reading level per page, from the plain text: Flesch-Kincaid grade at level 1 at most 9 and at
   level 2 at most 13 (thresholds assumed; the primer measures 7.1), grade rising from level 1
   to 3 within every topic, no sentence over 40 words (`generators/prose_lint.py:24`), and every
   word from a jargon list used at level 1 linked to the glossary on first use.
6. Banned reader-facing strings on learn pages: "verified", "proven", "confirmed", "✓",
   "MAJORITY_VERIFIED", "27-dimensional", "27D", "25D" (`claude-context.md:40`).
7. Links: every level link and research link resolves to an existing file and anchor; every level
   4 page in the map carries the link back down.
8. No borrowed value: a fixture path with one NOT_EVALUABLE claim renders the phrase, not the
   default path's number; a fixture with no `claims.json` shows the phrase everywhere.
9. No-go: a fixture path labelled no-go shows the rejection line on all four learn pages.

## 7. Points for P9 and for the owner

- `pm-path-context.js:16` and `:293` show main's file when a path's file is missing. On learn

  site-wide.
- `statistics.json:37` publishes "MAJORITY_VERIFIED" next to a POOR_FIT registry verdict. This
  proposal keeps it off learn pages; whether other pages should keep it is outside P10.
- The old guide and `beginner-guide.json` state retired facts (27D) and open with
  persuasion. This proposal retires both instead of editing them (S6). The owner decides whether
  any text from them is kept.
