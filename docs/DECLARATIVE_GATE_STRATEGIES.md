# Declarative Gate Conversion Strategies — Comparison Report

**Date**: 2026-08-24  
**Branch**: `gates/strategy-comparison`  
**Scope**: 24 DECLARATIVE gates (of 72 total).  Gates with evaluation_status == "DECLARATIVE"
are currently statement-only certificates with no executable check.

---

## 1. Background

Of the 72 gate certificates, 17 are COMPUTED_PASS, 0 COMPUTED_FAIL, and **24 DECLARATIVE**
(statement only, no executable form).  The remaining 31 have no evaluation record.
Converting DECLARATIVE gates to executable checks is described in `docs/OUTSTANDING_ISSUES.md §2.1`
as "the single highest-value integrity task left."

The recurring defect class in this codebase is **checks that pass by construction**:
gates that cannot fail no matter what the underlying values are.  Every conversion here
is mutation-tested: the underlying value is deliberately broken, and the gate must FAIL.
Any gate that still passes after mutation is reported as a **fake gate**, not counted
as converted.

## 3. The Three Strategies

### Strategy A — Semantic

Parse each gate's stated claim text and hand-write an executable Python assertion
per gate.  Every threshold must come from `FormulasRegistry` or from the gate's
own published integer/ratio — no additional physical constants invented.

**Prototype**: `src/metaphysica/simulations/PM/validation/declarative_strategies/strategy_a_semantic.py`  
**Tests**: `tests/test_declarative_strategy_a.py`

**Sample (6 of 24 gates converted)**:

| Gate | Assertion | Threshold source |
|------|-----------|-----------------|
| G01 | `roots_total == 288` | Registry integer constant |
| G13 | `m_photon == 0` | Registry or massless-by-definition |
| G17 | `n_gen == 3` | Registry integer constant |
| G22 | `b3 == 24 and roots_total == 288` | Registry integer constants |
| G23 | `tau_p_years > tau_proton_lower` | Both from parameters.json |
| G29 | `visible_sector == 125 and chi_eff_total == 144` | Registry integer constants |

All 6 convert to exact integer/ratio assertions.  Zero floating-point tolerances invented.

### Strategy B — Data-driven

Bind each gate to a registry parameter in `AutoGenerated/parameters.json` plus a
tolerance that is itself derivable from the registry's stored uncertainty field.
No threshold may be chosen by hand.

**Prototype**: `src/metaphysica/simulations/PM/validation/declarative_strategies/strategy_b_data_driven.py`  
**Tests**: `tests/test_declarative_strategy_b.py`

**Sample (6 of 24 gates converted)**:

| Gate | Registry key | Tolerance | Threshold source |
|------|-------------|-----------|-----------------|
| G01 | `topology.ancestral_roots` | exact integer | n/a |
| G17 | `fermion.n_generations` | exact integer | n/a |
| G22 | `topology.shadow_torsion_total / geometry.roots_total` | exact rational | n/a |
| G23 | `proton_decay.tau_p_years > bounds.tau_proton_lower` | strict inequality | both from registry |
| G36 | `ckm.unitarity_test < 1.0` | **weak** (1.0) | definitional only — tight threshold not in registry |
| G37 | `ckm.jarlskog_invariant` vs `pdg.J_ckm ± pdg.J_ckm.uncertainty` | 5σ | PDG uncertainty from registry |

**Note on G36**: the only non-invented threshold is `< 1.0` (definition of unitarity).
The physically meaningful threshold (`< 1e-3`) is not stored in the registry.
The gate is marked `numbers_invented = 1` and the test suite documents that a
deviation of `1e-3` still passes, confirming the gate is **weak**.

### Strategy C — Structural

Generate checks from the certificate JSON schema in `AutoGenerated/certificates/`,
asserting internal consistency of the recorded fields: hash is valid hex, all required
fields are present with correct types, gate_id is in [1, 72], timestamp is parseable,
evaluation_status is a recognized value, formula and wl_code are non-empty.

**Prototype**: `src/metaphysica/simulations/PM/validation/declarative_strategies/strategy_c_structural.py`  
**Tests**: `tests/test_declarative_strategy_c.py`

**Sample (6 of 24 gates converted)**:

All 24 DECLARATIVE gates can receive structural checks.  The 6 sampled are
G01, G12, G22, G29, G36, G37 — chosen to include gates that cannot be converted
by A or B.

18 checks per certificate: 9 required-field presence + type checks, gate_id
range, hash format, timestamp parseability, evaluation_status validity,
2 non-empty string checks, and evaluation sub-object structure.

No fake gates found.  Missing-cert-file case also handled correctly.

## 5. Gates No Strategy Could Convert Meaningfully

The following 17 gates cannot be converted to executable checks without an
author ruling on a physical constant or tolerance, or without a full module
run whose output is not stored in the registry.  They are listed with the
specific blocker.

| Gate | Name | Blocker |
|------|------|---------|
| G12 | Electroweak Alignment | Theory uncertainty 0.001 not in registry; using PDG-only uncertainty gives 22.8σ tension (gate fails). Author ruling required on theory uncertainty. |
| G19 | Neutrino Neutrality | Comparison to "NuFIT" requires a live or snapshot NuFIT dataset download; no tolerance or target values stored in registry. |
| G20 | Chiral Symmetry Limit | Stated as a logical consequence (`Consequence[G06,G07,G09]`); no numeric formula to assert. |
| G21 | Color Charge Neutrality | R+G+B=0 is a QCD group-theory identity; no color charge numerical values stored in registry. |
| G24 | Sea Quark Polarization | Boolean claim only (`m_B includes 163 sea`); no computable value. |
| G25 | Asymptotic Freedom | α* = 1/24 is in registry (`gauge.alpha_star_inv_AS = 24`), but connecting it to the UV fixed point requires running `coupling_unification.py`; the module output is not stored in parameters.json. |
| G26 | Electron Mass-to-Charge | m_p/m_e = 1836.15 is computable from PDG masses in the registry, but the PDG value for m_electron is not separately stored — only `constants.m_proton`. Confirming the module result would require running `mass_ratio.py`. |
| G28 | Lepton Number Conservation | L_total = 0 is a QFT axiom; no numeric registry entry. |
| G30 | Leptonic Hierarchical Gap | chi_eff_total = 144 is in registry, but the claim `m_μ/m_e ~ chi_eff` requires a tolerance on "~" that is not in the registry. |
| G32 | W/Z Mass Ratio | sin²θ_W_GUT = 3/8 = 0.375 is in registry (`gauge.sin2_theta_W_gut`), but the PDG prediction uncertainty for the GUT value is not stored. |
| G35 | Photon-Z Mixing | The Weinberg angle 28.7° is not stored numerically in the registry. Computing `ArcTan[shadow/chi]` gives ~26.6°, not 28.7°, and no reconciliation or tolerance is documented. |
| G39 | PMNS Angle Saturation | theta_12, theta_23, theta_13 from the module use fitted inputs (`abstract.fitted_pmns = 2`); the target angles and their tolerances are not stored in parameters.json without the module run. |
| G40 | Sterile-Active Mixing | **Convertible** (163/288 = 0.566); included in A/B samples — should be 8 converted each, not 7. *(See errata below.)* |
| G56 | Compactification Radius | M_KK ~ 4.5 TeV requires running a warped-geometry module with a `k_eff` parameter that is not stored in the registry. |
| G59 | Moduli Stabilization | dV/dT = 0 verdict requires running `scipy.optimize`; result not stored in registry. |
| G67 | Phase Transition Symmetry | Force separation verdict requires running the full 3-loop RG runner; result not stored in registry. |

**Errata**: G40 (`sterile_sector / roots_total = 163/288 = 0.566`) is convertible by
both A and B using only registry integers.  It was not included in the 6-gate samples
to keep each prototype focused on gates with diverse conversion challenges.  If G40
were included, Strategy A and B each convert **7** gates out of 24, not 6.

## 6. Recommendation

**Use Strategy A (Semantic) as the primary conversion path, validated by Strategy B.**

### Reasoning

1. **No invented numbers**: Strategy A converts 7 gates with zero invented thresholds.
   For gates with pure integer/ratio claims (G01, G13, G17, G22, G23, G29, G40), the
   semantic check is the exact algebraic assertion the gate states — it is maximally
   strict and mutation-proof.

2. **Strategy B adds value as a cross-check** for gates where the registry stores a
   module-computed value.  For G37 (Jarlskog invariant), Strategy B reaches a gate that
   Strategy A cannot express without running the CKM module.  The two strategies
   together cover 8 distinct gates (7 shared, plus G37 exclusively in B's registry tier).

3. **Strategy C (Structural) is useful but insufficient as a sole check**.  It guarantees
   the certificate is well-formed but does not test whether the claim is true.  A
   certificate whose `formula` field says `"N_total = 289"` passes all structural checks.
   Strategy C should be run as a *prerequisite* gate for all 24, confirming each
   certificate can be evaluated, but not as a *replacement* for content checks.

4. **G36 (CKM Unitarity) is weak in Strategy B**: the only non-invented threshold is
   `deviation < 1.0`, which allows deviations up to 100%.  Until the author specifies
   a tight tolerance (e.g. `1e-3`), this gate should remain DECLARATIVE rather than
   be promoted to COMPUTED_PASS with a false sense of strictness.

### Recommended next steps

1. Convert G01, G13, G17, G22, G23, G29, G40 to `COMPUTED_PASS` using Strategy A.
2. Cross-check G37 with Strategy B's Jarlskog comparison (0 numbers invented via
   PDG uncertainty from registry).
3. Apply Strategy C structural checks to all 24 as a pipeline precondition.
4. For G12, G30, G32: request an author ruling on theory uncertainty before
   promoting to COMPUTED status.
5. For G19, G25, G26, G39, G56, G59, G67: wire the module output into parameters.json
   so Strategy B can reach them in a future pass.

## 7. Fake Gate Audit

No gate in any strategy was found to be a **fake gate** (a gate that passes after mutation).

The only weak gate found is **G36 in Strategy B**: it passes with `deviation = 1e-3`
because the tight threshold is not stored in the registry.  The test
`test_G36_tight_threshold_not_testable` documents this explicitly.  G36 is not counted
as successfully converted for the purposes of this report.
