# CLAUDE.md — `metaphysica` package

Guidance for Claude Code working inside the `metaphysica` PyPI package
source tree.

## What this is

The `metaphysica` package is the **engine + generators + website
templates** behind the Principia Metaphysica framework. It's published
to PyPI and consumed by:

- [`PrincipiaMetaphysica`](https://github.com/andrewkwatts-maker/PrincipiaMetaphysica)
  — thin static-site host. Calls `metaphysica.build()` to render the site.
- [`metaphysica-app`](https://github.com/andrewkwatts-maker/metaphysica-app)
  — interactive PC + APK GUI on top of the same engine.
- (future) `periodica` — materials-science layer; will call
  `metaphysica.Get('Up')` to source quark/constant data instead of
  shipping its own static JSONs.

## Standard commands

```bash
pip install -e .[full]                   # editable install with every extra
pytest                                   # full test suite (~20s)
python -m metaphysica.build --out ./site # full website rebuild into ./site
python -m metaphysica.generators.generate_datasheets   # refresh bundled snapshots
python -m build && python -m twine check dist/*        # build wheel + sdist
```

## Public API

- `metaphysica.Get(name, *, as_json=False)` — JSON datasheet for a quark
  or named constant. Bundled-fast-path; no sim run required.
- `metaphysica.list_quarks()` / `metaphysica.list_constants()` — listings.
- `metaphysica.build(out_dir, *, fast=False, skip_sims=False, only=None)`
  — full website regeneration.
- CLI: `metaphysica-build`, `metaphysica-datasheets`.

## Optional extras

Base `pip install metaphysica` is intentionally slim (numpy / scipy /
sympy / mpmath / eml-math). Anything heavier is gated behind an extra:

| Extra | Adds | Enables |
|-------|------|---------|
| `[sims]` | eml-spectral | full sim runs (advanced algebras: E8, Leech, octonions) |
| `[plots]` | matplotlib, pandas | visualisation plot regeneration |
| `[pdf]` | xhtml2pdf | PDF paper export |
| `[full]` | all of the above | recommended for `metaphysica-build` |
| `[dev]` | pytest, black, mypy, build, twine | development + release |

`build.py` skips steps whose extras are missing with a friendly install
hint instead of failing — so a slim install never produces a broken build.

## When you change theory

If you touch any file under `simulations/PM/` that affects a constant
or quark mass, refresh the bundled snapshots so `Get()` returns the new
values:

```bash
python -m metaphysica.generators.generate_datasheets
```

The `Generate quark + constant datasheets` build step does this for you
automatically as part of `metaphysica-build`.

## Versioning — 4 locations must stay in sync

When bumping the package version, **all four locations must be updated together** or the PyPI release will be broken:

| File | Field |
|------|-------|
| `pyproject.toml` | `version = "X.Y.Z"` under `[project]` |
| `rust/physica_core/Cargo.toml` | `version = "X.Y.Z"` under `[package]` |
| `src/metaphysica/__init__.py` | `__version__ = "X.Y.Z"` |
| Git tag | `vX.Y.Z` pushed to origin |

After committing and tagging, create a **GitHub Release** from the tag to trigger the PyPI publish workflow (`release: published` event). The workflow does **not** fire on a tag push alone.

> **Important:** `pyproject.toml version` is what PyPI indexes — not the git tag. Pre-release suffixes like `2.0.0a0` are **not** matched by `>=2.0.0` in pip. Always use clean `X.Y.Z` for stable releases.

## Project Philosophy & Senior Development Standards

These reflect senior-level software engineering discipline: clarity,
maintainability, extensibility, automation, and long-term sustainability.

### 1. Core Architectural Principles (SOLID + Beyond)

Apply SOLID principles rigorously:
- **Single Responsibility:** each class / module has one clear reason to change.
- **Open / Closed:** entities are open for extension but closed for modification.
- **Liskov Substitution:** subtypes must be fully substitutable for base types.
- **Interface Segregation:** prefer small, client-specific interfaces over large ones.
- **Dependency Inversion:** depend on abstractions, not concretions.

**DRY + Strategic Generalization:** aggressively eliminate duplication. When
similar logic appears across modules or projects, extract it into well-designed
base classes, abstract base classes, or shared libraries using proper
inheritance and composition. Favor composition over inheritance when behaviour
is likely to vary.

**Separation of Concerns:** keep UI, business logic, data access, and
configuration strictly separated.

**Configuration Management:**
- Use YAML for all configuration files (human-readable, supports comments,
  hierarchical).
- Exception: Unreal Engine projects → use JSON or `.ini` as appropriate for
  the engine.

### 2. Python-Specific Standards

- **UI Layer:** every Python project with a graphical interface must use
  KivyMD (Material Design for Kivy) for consistency, modern look, and
  cross-platform capability.
- **Build & Distribution:**
  - Every Python project must include a `build.bat` (Windows) and an
    equivalent shell script for other platforms.
  - The build must produce a single executable (via PyInstaller or equivalent).
  - Target ≥ 90 % code coverage on unit + integration tests before producing
    the final EXE.
  - Include automated linting (ruff / black), type checking (mypy or pyright),
    and tests as part of the build pipeline.

### 3. Documentation Standards

- Every project must maintain up-to-date HTML documentation focused on
  "How To" basics (setup, common tasks, architecture overview, key workflows).
- For production / launch projects, documentation should be auto-generated
  where possible (e.g. from docstrings, markdown, or OpenAPI specs via
  Sphinx / MkDocs).
- Keep the documentation in the repository root or `/docs` folder and
  version-controlled.

### 4. Additional Senior Engineering Practices

**Code Quality & Maintainability:**
- Clear, self-documenting code with meaningful names.
- Comprehensive but focused unit and integration tests.
- Logging and error handling that aids debugging without verbosity.
- Consistent naming conventions and project structure across repositories.

**Reusability & Scalability:**
- Design components to be reusable across projects.
- Extract common functionality into internal shared packages / libraries
  when patterns emerge.

**Automation First:**
- Automate builds, tests, packaging, and documentation generation.
- Minimise manual steps required to go from clone → run → deploy.

**Security & Performance Awareness:**
- Validate inputs, handle secrets securely, and be mindful of resource usage.
- Profile critical paths and optimise when necessary.
